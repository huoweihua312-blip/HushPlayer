# HushPlayer 用户体验闭环优化设计

## 背景

前两轮用户视角审查发现，HushPlayer 的基础视觉已经稳定，但仍有几类影响信任感的问题：部分入口不容易发现，部分右键动作没有接到真实处理逻辑，沉浸歌词的设置存在重复命名和隐藏功能，空音乐库和异步操作的下一步不够明确。

## 目标

1. 让空音乐库、沉浸歌词和歌曲右键菜单都具备清晰、可完成的下一步操作。
2. 让沉浸歌词在普通窗口、全屏、暂停、歌词加载失败和设置修改场景下都保持可控。
3. 保持现有播放、队列、歌词同步和持久化 JSON 结构不变。
4. 使用现有主题令牌和控件模式，不引入第三方依赖，不进行大规模文件拆分。

## 实施顺序

### 第一批：沉浸歌词与首次使用体验

- 为沉浸歌词增加可见的全屏入口，同时保留 F11 快捷键。
- 增加翻译和罗马音的显示开关，避免用户必须返回普通歌词页调整。
- 拆分背景相关设置的用户文案和应用逻辑，避免两个“背景透明度”互相覆盖。
- 增加恢复沉浸歌词默认设置的操作，并沿用现有预览、取消、保存事务流程。
- 调整控制层自动隐藏策略，暂停或打开面板时保持可见。
- 为图标按钮补充辅助名称和键盘提示。
- 在空音乐库状态提供添加音乐文件夹入口，并复用现有设置/扫描动作。

### 第二批：主界面操作闭环

- 将歌曲右键菜单的“添加到歌单”接到现有歌单适配器。
- 将“查看歌曲信息”实现为只读详情窗口；不新增持久化数据。
- 保留单击浏览、双击播放的既有习惯，并为单击详情提供明确但不打断播放的表面。
- 增加“更多”导航分组，暴露最近播放、歌手、专辑和普通歌词。
- 为待导入数量、扫描结果、在线匹配和歌词失败提供持久的非模态反馈。
- 对忽略待导入操作增加说明清楚的确认。

## 交互和数据边界

- 添加到歌单只在用户明确选择歌单后调用现有 `PlaylistAdapter`；不改变歌单 JSON 结构。
- 详情窗口只读展示当前 `Track` 的已有字段，不上传本地路径，不启动播放。
- 沉浸歌词设置继续通过现有 `SettingsBridge` 保存，缺失旧字段时使用安全默认值。
- 全屏仍使用当前主窗口，不创建第二个播放器或第二个媒体实例。
- 空音乐库的“添加文件夹”只打开已有音乐库设置和扫描流程，不在空状态中直接执行不可逆操作。

## 风险和保护范围

- 不重写 `QMediaPlayer`、播放队列、播放上下文或歌词时间线。
- 不迁移或重排 `library.json`、`playlists.json`、`stats.json`。
- 不删除旧兼容入口；隐藏入口只在已有路由支持的基础上补充可见导航。
- 右键菜单和歌单写入属于用户主动操作，失败时必须保留当前页面和播放状态，并给出可理解的反馈。
- 若详情窗口、歌单选择或真实库设置连接无法在当前架构中安全完成，优先移除无效菜单项或提供只读替代，不保留无响应按钮。

## 验证

- 修改 Python 文件后逐文件运行 `py_compile`。
- 运行沉浸歌词、播放适配器、歌单、真实交互和相关页面测试；环境缺少依赖时如实记录。
- 检查沉浸歌词的普通窗口、全屏、暂停、设置保存/取消、翻译/罗马音、无歌词和歌词失败状态。
- 检查空音乐库添加文件夹、右键菜单、歌单写入、详情窗口和导航可见性。
- 最终运行 `git diff --check`，只提交本轮相关文件。

## 回滚

第一批和第二批在本次提交中保持文件范围清晰；若某个交互连接引发回归，可按对应文件范围回滚，不触碰用户数据、发布配置和播放核心。
