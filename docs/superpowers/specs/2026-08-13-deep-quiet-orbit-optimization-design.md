# HushPlayer 深度用户体验优化设计

## 背景

HushPlayer 当前已具备 Quiet Orbit 主外壳、真实音乐库、歌单、收藏、在线来源、失效歌曲恢复、歌词和应用内更新能力。下一阶段重点不是重新做一套播放器，而是把用户每天反复使用的路径变得更直接、更安静、更可靠。

## 目标

1. 让用户在启动后能够快速理解当前位置、当前播放内容和下一步可做的事情。
2. 让音乐库、我喜欢、歌单、在线搜索和失效歌曲恢复拥有一致的信息层级与操作语言。
3. 让 900、1024、1280、1440 像素宽度下的列表、底栏、导航和弹窗都保持可用，不出现遮挡或横向溢出。
4. 降低启动和页面切换的感知等待，但不改变媒体播放器、播放队列、用户数据结构和在线来源协议。
5. 所有异步动作都给出清楚的阶段、结果和可恢复操作。

## 非目标与保护范围

- 不迁移或重写 `library.json`、`playlists.json`、`stats.json` 或用户设置结构。
- 不替换 `QMediaPlayer`、播放队列、在线来源协议或更新助手。
- 不删除旧 UI、兼容入口、正式发布产物或用户数据。
- 不添加第三方依赖。
- 不将视觉优化变成大规模文件拆分或主窗口重写。

## 实施顺序

### 第一批：外壳与视觉层

- 统一标题栏、侧边栏、页面标题、内容区、列表和底部播放器的层级。
- 让导航在默认宽度下突出音乐库、浏览、我喜欢、在线搜索和歌单；低频页面保留可发现入口，不增加重复入口。
- 优化列表行高、列可见性、当前播放/选中/悬停/失效状态和空状态。
- 为常用页面补充稳定的内容边距、操作区和窄窗口布局。
- 保留键盘焦点、工具提示和可访问名称。

### 第二批：高频功能流程

- 收藏和取消收藏保持即时、明确且不依赖歌曲是否可播放。
- 歌单中的失效歌曲提供在线查找、直接替换播放来源和失败后的恢复入口。
- 替换播放来源只更新来源字段，不删除歌单成员关系、收藏关系、排序位置或用户元数据。
- 在线搜索和来源管理使用一致的加载、空结果、失败、禁用和重试反馈。

### 第三批：播放与性能

- 播放器底栏继续保证标题、收藏、播放控制、进度、队列、歌词和音量在常见窗口中不互相遮挡。
- 只优化已经存在的后台 worker、缓存、页面缓存和可见区域刷新；不改变真实库的加载状态契约。
- 为启动、首帧、首次可交互、页面切换和列表刷新保留可测量日志。
- 异步加载过程中预留布局空间，减少内容跳动和重复重绘。

## 视觉方向

- 继续使用 Quiet Orbit 的深色优先、低饱和金色强调色、柔和表面层和有限圆角。
- 内容优先：结果列表和当前播放内容拥有最高视觉权重，装饰性卡片和无效按钮不占空间。
- 主操作使用明确动词，例如“播放全部”“替换播放来源并播放”“重试来源”。
- 选中、播放中、悬停、失效和禁用状态使用不同层级，不只依赖颜色表达。
- 长标题、艺人、专辑和来源统一省略显示，并通过工具提示保留完整文本。

## 技术策略

- 优先修改独立的 V2 widget、page 和 theme token，不直接重写 `main_window.py`。
- 每批修改后运行对应的 unittest、烟测、`py_compile` 和 `git diff --check`。
- 每批独立提交，保证可以按批回滚。
- 只提交本轮明确修改的文件；保留既有未跟踪的 `CLEANUP_AUDIT.md`。

## 验收标准

- 1024px 窗口下播放器收藏按钮、播放按钮和进度条完整可见。
- 音乐库、我喜欢、歌单和在线搜索至少经过空状态、加载状态、失败状态和有内容状态检查。
- 右键、双击、收藏、歌单和在线恢复操作不破坏当前播放上下文。
- 主题切换后文字、按钮、列表选中态和禁用态仍保持可读。
- 现有用户数据、来源禁用状态和更新流程兼容。

## 回滚

每批使用独立的 Conventional Commit。本设计及实现只在本地提交，不自动推送远端；如某批产生回归，可回滚对应提交而不影响用户数据、Git tag 或 Release。
