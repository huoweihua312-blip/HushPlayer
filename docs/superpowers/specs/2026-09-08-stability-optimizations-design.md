# HushPlayer 稳定性改进：范围、验证与后续方案

日期：2026-09-08。依据：用户确认执行源码审查建议；按小步改进开展。

## 本轮设计与实现范围

保留 UI V2、现有 JSON 格式和播放控制接口。在现有读写边界与列表适配层改进，比迁移数据库或整体替换界面架构更容易验收和回滚。仅更新文档无法解决已发现的缓存与容错问题，因此本轮同时实施以下局部修复：

1. 缓存：原图、缩放图片、默认封面分别设置 32、64、16 MiB 的估算像素缓存预算及 128、512、128 条上限，按最近使用顺序淘汰。单张超预算图片仍可显示，但不驻留缓存。预算不代表进程总内存上限；可见控件、Qt/GPU 开销另计。同路径文件依据修改时间、大小及封面键失效。
2. 设置：不存在的文件使用独立默认值；损坏、非对象根节点或无法读取的文件允许应用采用默认显示，但保存前重新校验原文件，拒绝覆盖并通过既有错误反馈提示用户。读取失败记入诊断日志。不会自动备份、修复或删除用户文件。
3. 曲库：整份 JSON 无法解析时仍报错；可解析列表中的异常条目按条跳过，正常条目保留未知字段。保持旧版空对象与暂时不可用文件的读取兼容行为。跳过数量通过加载状态传至界面；播放统计的异常条目写入诊断日志。仓库仍只读。
4. 列表：共享惰性搜索文本缓存、单曲行号索引；记录更新或整体刷新时失效。排序键变化才重排，其余更新保持单行刷新。表格重置按歌曲 ID 恢复仍存在的选择、保留滚动值，不发起播放。歌单原有成员顺序分支保留。
5. 文档：正式入口统一为 UI V2；明确 CPython 3.13 x64 构建目标和现有可用环境本地验证的区别。提供临时数据目录下的稳定性回归入口。

## 手工验收

1. 手动备份项目及用户数据后，正常启动，确认曲库、收藏、歌单、设置仍能读取。
2. 播放歌曲 A，单击浏览 B，再搜索、排序、切换我喜欢和歌单：听到的歌曲和暂停状态应保持原状。
3. 按时长排序，播放尚未补齐时长的歌曲：时长更新后排序应正确；仍在列表中的选中歌曲保持选中。清空搜索应返回完整列表。
4. 连续浏览封面、调整窗口大小、切换主题，观察封面无错配、无旧图残留；缓存淘汰后重新显示图片允许再次解码。
5. 在临时测试数据副本中加入坏记录，正常歌曲仍显示，音乐库提示跳过数量；播放统计异常有诊断日志。不要直接破坏正式用户数据。
6. 在临时副本中破坏设置 JSON，启动后尝试保存：应提示无法覆盖，原文件字节不变；手动修复副本后重新打开设置可正常保存。
7. 检查双击播放、暂停、上一首/下一首、桌面歌词、沉浸歌词和关闭窗口，确认没有关联回归。自动测试不能替代真实声音和多屏验收。

## 回滚

本轮不迁移用户 JSON、不升级依赖。需要回滚时，可在检查无未提交用户改动后撤销本轮单独提交；这需要用户明确请求，不自动执行。被跳过的坏记录仍留在原文件内，可在备份后人工修复。

## 后续高风险工作：需独立确认

### 失联歌曲管理

现有读取层跳过不存在的本地路径。建议下一阶段让只读投影保留失联条目并显示不可用状态，再设计手动重新定位。涉及 `LibraryRepository.load_library_records`、`RealLibraryAdapter.map_snapshot`、歌曲菜单及播放前可用性检查。风险是临时不可用路径的处理、歌单身份关联和重新定位后的兼容性。较低风险替代是先显示失联数量、不改成员映射。回滚需还原该独立功能提交；如果实施路径重绑定，还需先定义用户数据恢复方案。

### 线程退出与资源回收

`RealLibraryAdapter.shutdown` 与 `_on_thread_finished` 应先测试慢磁盘、不可用网络目录、刷新途中退出。候选方案是在安全点检查中断并在 Qt 对象生命周期明确结束后释放线程包装；风险是尚未完成 I/O 时销毁对象、阻塞退出或迟到信号访问关闭窗口。较低风险方案是先补生命周期诊断和压力测试。推荐在可模拟慢 I/O 的独立任务中实施，单独提交以便回滚，本轮不改线程架构。
