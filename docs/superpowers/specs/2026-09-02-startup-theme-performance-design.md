# HushPlayer 启动与主题切换性能优化设计

## 背景

当前启动日志显示，首屏前主要耗时来自在线音频缓存 SQLite 首次建表、完整 Shell/UI 构建、全局 QSS 与控件样式应用；首屏显示后，音乐库卡片和封面刷新仍可能在 UI 线程集中发生。深浅色切换时，主题揭示动画在 `MainWindow.set_theme()` 完成之后才启动，而该函数会同步刷新应用和多个页面的样式，因此点击后会出现明显等待。

## 目标

1. 缩短启动到可交互首屏的阻塞时间，降低首屏后列表与封面集中刷新造成的卡顿。
2. 让主题切换在点击后尽快给出视觉反馈，并避免所有主题刷新工作挤在一次长同步调用中。
3. 保持播放、播放队列、歌词解析与同步、桌面歌词、沉浸歌词、数据文件格式和现有交互习惯不变。

## 方案

### 启动阶段

- 保留现有真实音乐库快照的后台读取和映射线程。
- 在线音频缓存保留现有同步数据库接口，但将首次 SQLite schema 建立改为首次数据库访问时懒初始化；启动清理延后到应用稳定后的空闲时段。
- 主窗口显示后，将真实库加载完成后的 UI 投影拆成有限的事件循环批次：先更新必要的播放状态和可见内容，再处理卡片刷新、封面请求等非首屏关键工作。
- 每个批次只做一次明确的 UI 更新，不启动新的扫描，不重复读取 JSON，不改变歌曲身份或排序规则。
- 增加阶段性诊断点，分别记录后台加载完成、列表投影、封面请求和首屏后批次的耗时，便于验证卡顿是否真正下降。

### 主题切换阶段

- 保留当前 `ThemeRevealOverlay` 和主题截图效果。
- 点击后先创建并显示遮罩，让 Qt 尽快回到事件循环并绘制首个反馈帧。
- 将主题状态、全局样式、根窗口样式、页面样式和图标更新拆成有顺序的 UI 批次；批次之间允许事件循环处理动画绘制。
- 设置保存安排在主题应用完成后执行；保存失败时不阻断界面恢复，并沿用现有错误处理。
- 使用统一的完成回调恢复 `updatesEnabled`、清理遮罩和清除调度状态，避免重复点击、异常或窗口关闭时残留锁定状态。

## 数据流与状态保护

启动流程保持：后台读取快照 → UI 线程接收结果 → 分批投影到页面。批次调度只改变时间顺序，不改变数据内容。

主题流程保持：点击目标主题 → 显示遮罩 → 分批应用主题 → 保存设置 → 结束揭示动画。切换期间使用现有主题快照和单次调度标记，重复点击不创建并行主题切换。

## 错误处理

- 启动后的任一 UI 批次失败时，记录诊断信息并继续执行可安全执行的收尾步骤；不得让主窗口永久处于禁用更新状态。
- 主题批次失败时恢复根窗口和主窗口的更新状态，清理遮罩；设置文件仍保留原有快照保存策略。
- 不在后台线程直接操作 Qt 控件，不把 QSS、图标或页面更新移出 UI 线程。

## 验证标准

- 启动日志能区分首屏前耗时和首屏后各 UI 批次耗时；首屏显示后不再出现明显的一次性长刷新。
- 点击深浅色按钮后，在可感知的短时间内出现遮罩/动画反馈；切换完成后所有页面、标题栏、播放器栏、设置和桌面歌词主题一致。
- 连续快速点击主题按钮、在设置页切换主题、关闭窗口和无音乐库场景均不死锁、不残留遮罩。
- 播放/暂停、切歌、进度、音量、歌词同步、桌面歌词拖动与穿透行为保持正常。
- 运行 Python 语法检查、现有相关 Smoke 测试、启动诊断测试和 Git 差异检查。

## 风险与回滚

主要风险是批次调度改变了刷新时序，可能暴露某个页面对“同步完成”的隐含依赖。实现时只在现有回调和主题入口内增加调度，不改变核心接口；若出现回归，可单独回退本次提交，恢复原有同步刷新路径。
