# 桌面歌词拖动与切歌布局稳定性设计

## 背景

桌面歌词在长歌词切换到短歌词后，窗口宽度按当前产品规则保持不缩小，位置也应保持不变。但用户反馈：此时再拖动歌词，拖动过程中和释放鼠标后都会出现歌词闪烁与位置跳动。

当前 `DesktopLyricsWindow` 已优先使用 Windows `QWindow.startSystemMove()` 拖动。与此同时，歌词切换、播放进度和设置预览仍可能调用 `_render()`、`_apply_content_height_floor()` 或实时 `resize()`。这些操作与系统原生窗口移动同时发生时，会让窗口的几何尺寸、视觉中心和系统拖动位置互相竞争。

## 目标

1. 拖动期间保持窗口几何稳定，不因歌词重绘、切歌或预览更新而移动或缩放窗口。
2. 仍然允许歌词文字在播放过程中正常更新，不暂停歌词同步。
3. 松开鼠标后，只合并执行一次必要的窗口尺寸调整，并继续使用视觉中心锚定。
4. 保持两行歌词、鼠标穿透、锁定按钮、右键设置和位置持久化行为不变。
5. 不改变播放、队列、歌词时间轴解析和持久化 JSON 结构。

## 非目标

- 不替换 `QMediaPlayer` 或播放状态管理。
- 不重写歌词解析和歌词适配器。
- 不拆分 `main_window.py` 或调整桌面歌词窗口的整体架构。
- 不在拖动期间强制缩短已经自动扩展的歌词窗口。

## 方案

### 1. 拖动期间冻结窗口几何

在 `DesktopLyricsWindow` 内增加一次性的“拖动期间需要布局”状态。进入拖动后，窗口可以更新两个歌词标签的文字，但所有会改变顶层窗口位置或尺寸的操作都延后：

- `_apply_content_height_floor()` 仍计算当前歌词所需尺寸，但拖动进行时不调用 `resize()` 和 `_restore_window_center()`，只记录待处理状态。
- `apply_settings(..., live_preview=True)` 在拖动进行时不直接调整顶层窗口尺寸；字体、颜色等视觉预览仍即时应用。
- 锁定按钮在拖动期间继续隐藏，避免其独立窗口重定位引起额外重绘。

### 2. 释放后合并一次布局

`_finish_drag()` 清理原生拖动状态并持久化最终位置后，排队执行一次布局刷新。刷新时重新读取当前歌词和字体实际度量：

- 只在确实需要时改变窗口尺寸。
- 尺寸变化继续以释放后的窗口视觉中心为锚点。
- 已经满足当前歌词的窗口不重复 `move()`，避免释放后出现二次跳动。
- 如果释放前没有产生任何需要调整的几何变化，则不执行额外刷新。

这样可以覆盖“长歌词→短歌词→拖动”和“拖动过程中刚好切换歌词”两种路径。

### 3. 测试覆盖

新增回归测试验证：

- 拖动中切换为长文本时，窗口位置和尺寸保持不变，歌词文字仍可更新。
- 释放拖动后，待处理布局只执行一次，并保持视觉中心。
- 长歌词切换到短歌词后再次拖动，不会遗留待处理状态导致释放后跳动。
- 原有原生拖动/兼容回退、两行显示、自动扩宽和滑块样式测试继续通过。

## 风险与回滚

主要风险是拖动过程中字体预览或歌词切换后的尺寸调整会延迟到释放鼠标后，属于有意行为，以保证窗口移动稳定。文字内容本身不延迟。

若真实 Windows 测试仍有跳动，可回滚本次提交；回滚只涉及桌面歌词窗口、对应回归测试和更新日志，不影响播放及用户数据。
