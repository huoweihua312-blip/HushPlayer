# HushPlayer 默认 Legacy UI：歌单、音源与播放性能设计

日期：2026-08-11
目标运行路径：默认启动的 Legacy UI（执行 `python main.py`，不带 `--ui-v2`）
状态：待用户审阅，尚未实现

## 背景

当前用户反馈集中在四个相互关联但风险不同的问题：

1. 歌单歌曲缺少清晰、可靠的删除/取消收藏入口；“我喜欢”需要爱心操作，底部播放栏也需要保持状态一致。
2. 在线搜索中的音源管理入口较深；禁用音源后用户容易误以为音源被删除，且再次输入同一 URL 时会被当作重复来源跳过。
3. 在线歌曲首次播放和切换时有卡顿。
4. 启动等待时间较长，运行过程中存在界面响应卡顿。

当前默认入口仍是 Legacy UI。UI V2 是可选入口，真实模式的在线播放尚未接入，因此本轮不把修复放到 UI V2。

当前工作树包含一批 UI V2 的未提交用户改动。本设计不覆盖、不整理、也不提交这些已有改动。

## 目标

### 功能目标

- 歌曲列表中的收藏状态可以直接通过爱心操作切换。
- 在“我喜欢”视图取消收藏后，歌曲从当前视图立即消失，但不删除本地文件、在线记录或其他歌单成员关系。
- 底部播放栏的爱心按钮与统一收藏状态保持同步，避免按钮显示与数据状态不一致。
- 在线搜索页提供直达“自定义来源”管理的入口。
- 禁用来源仍保留在来源管理列表中，能够直接重新启用。
- “禁用”和“移除”在视觉和数据行为上明确区分。
- 对已注册但已禁用的同一 URL，提示用户重新启用已有来源，而不是静默当作重复安装。

### 性能目标

- 在线切换不再重复处理已经取消的旧请求，不让旧结果覆盖当前歌曲。
- 优先命中已有合法本地音频缓存，减少重复解析和重复网络等待。
- 首屏先显示可交互的主窗口，再延迟非必要的在线音源初始化、来源刷新和其他可延期工作。
- 降低重复读取、重复刷新列表和重复元数据/封面请求。
- 通过测量结果决定后续优化，不以增加线程数量作为默认目标。

## 非目标与保护范围

- 不切换默认 UI，不把 UI V2 改成默认入口。
- 不重写 `QMediaPlayer`、播放队列、播放上下文或歌词同步架构。
- 不迁移 `library.json`、`playlists.json`、`stats.json` 到新数据格式。
- 不删除本地文件、远程歌曲记录、用户歌单成员或用户音源文件。
- 不绕过商业平台会员、登录、地区、DRM 或版权限制。
- 不新增第三方依赖。
- 不为了“优化”改变单击浏览、双击播放、右键菜单等既有交互习惯。

## 推荐方案：分两个实施阶段

### 阶段一：低风险的功能修复

#### 1. 收藏与歌单成员操作

- 复用现有统一收藏 API `set_media_item_liked` / `toggle_liked_media_item`，不新建另一套收藏状态。
- 在 Legacy 歌曲列表的可操作区域补齐爱心入口；爱心应明确显示未收藏、已收藏和不可操作状态。
- “我喜欢”视图中的取消收藏调用现有 playlist membership 删除逻辑，只移除 `liked` 成员。
- 删除后刷新当前视图、收藏状态信号和底部播放栏状态；如果当前播放歌曲被取消收藏，播放继续，不中断播放。
- 保留已有右键“从我喜欢移除”和“从当前歌单移除”作为辅助入口。
- 检查底部播放栏现有 `likeButton`：若控件已存在，则修复显示、启用条件和状态同步，不创建重复按钮。

#### 2. 音源管理可发现性与启停语义

- 在 Legacy 在线搜索页的来源选择区域增加“管理来源”直达按钮，直接打开现有 `CustomSourceManagerPage`。
- 来源搜索选择器只展示已启用且具备搜索能力的来源，这是搜索行为；来源管理列表展示所有已注册的用户来源，包括已禁用来源。
- 管理列表中明确展示“已启用/已禁用”，按钮使用“启用来源/禁用来源”，不使用容易误解为删除的单一“开关”文案。
- `SourceRegistryManager.set_enabled` 继续负责启停持久化；`remove_source` 只由明确的“移除来源”动作调用。
- 修改重复 URL 处理：
  - 已存在且启用：提示已注册，不重复下载。
  - 已存在但禁用：提示该来源已存在且被禁用，并提供重新启用路径；不删除旧记录，也不创建重复记录。
  - 用户明确移除后再次添加：仍允许按正常流程重新注册。
- 刷新 Node 音源进程和统一搜索源状态时，忽略旧请求结果，避免禁用/启用后的短暂状态倒退。

### 阶段二：测量驱动的性能优化

#### 1. 在线播放切换

先在现有播放流程中增加轻量计时和状态诊断，区分以下时间：

`点击歌曲 → 取消旧请求 → resolvePlayback → 元数据/封面请求 → setSource → 首次 PlayingState`

随后只做局部优化：

- 保留播放 generation/identity 校验和旧请求取消机制，并检查所有异步回调是否都使用当前 generation。
- 切换时优先检查已有合法完整缓存；缓存命中时直接走本地文件播放。
- 避免切歌期间重复触发不影响首播的封面、歌词和详情刷新；这些内容允许异步补齐。
- 复用 `OnlineAudioCacheService` 的异步网络流，不在 UI 线程读取或哈希完整音频文件。
- 只在测量确认收益后考虑下一首预解析/预缓存；预缓存不能改变用户当前播放行为，也不能无控制地增加网络流量。
- 不把 `QMediaPlayer` 移入工作线程；Qt 多媒体对象继续留在拥有 GUI 事件循环的线程中。

#### 2. 启动与交互响应

- 继续使用现有启动计时点，建立构造、首屏、音源进程启动和首轮事件循环的基线。
- 先构造并显示主窗口，再通过 `QTimer.singleShot(0, ...)` 或等价的生命周期钩子启动可延期的在线音源初始化和来源刷新。
- 能够按需创建的管理页、详情页和非首屏服务采用延迟初始化，但不改变用户入口。
- 合并重复的库读取、列表刷新、来源刷新和状态同步。
- 仅当存在明确的 CPU/IO 阻塞证据时才使用后台 Worker；QObject/QProcess/网络对象保持正确的线程归属和事件循环。
- 不在启动优化中重新构建完整安装包或改变打包结构。

## 备选方案及取舍

### 方案 A（推荐）：局部修复 + 测量驱动优化

修改现有 Legacy 页面、列表交互和服务边界，优先修复用户可见问题，再按计时结果做小范围性能优化。

- 优点：范围可控，能复用现有数据兼容和播放恢复逻辑，回滚简单。
- 风险：不能一次消除所有网络抖动；部分性能问题可能需要后续专项工作。
- 适用：当前版本稳定性优先的修复。

### 方案 B：统一 Legacy/UI V2 在线状态并引入后台 Worker

让两套 UI 共用统一在线搜索/源管理适配层，同时把解析、索引和部分启动任务迁移到 Worker。

- 优点：长期减少重复实现，性能优化空间更大。
- 风险：会触及 UI V2、线程归属、播放信号和兼容测试，回归范围明显扩大。
- 结论：不作为本轮首选，可在阶段一稳定后单独立项。

### 方案 C：重写播放与启动架构

重建播放控制器、在线缓存和启动生命周期。

- 优点：架构自由度最高。
- 风险：最容易破坏播放队列、歌词、恢复播放、缓存和用户数据兼容性。
- 结论：本轮不采用。

## 测试与验收

### 自动检查

- 修改过的 Python 文件逐个执行 `py_compile`。
- 执行 `git diff --check`，并确认没有意外的编码变化或中文乱码。
- 歌单/收藏：运行现有 playlist membership smoke，并新增/补充“我喜欢取消收藏后立即消失、播放不中断”的检查。
- 音源：运行 source management/removal smoke，并新增“禁用后仍可见、重新启用、移除后可重新注册”的检查。
- 在线播放：运行现有在线播放和缓存 smoke，覆盖旧请求取消、缓存命中、切换后旧回调不覆盖新歌曲。
- 启动：运行现有启动性能 smoke，记录优化前后构造时间、首屏时间、线程/进程残留和重复读取计数。

### 人工验收

1. 在默认 Legacy UI 中打开“我喜欢”，点击歌曲爱心，确认加入/移除立即生效。
2. 在普通歌单中移除歌曲，确认只移除歌单成员，不删除音乐文件。
3. 播放歌曲后点击底部爱心，再进入“我喜欢”确认状态一致。
4. 从在线搜索页直接进入来源管理，禁用来源后确认它仍显示并可重新启用。
5. 对已禁用来源再次输入同一 URL，确认不会出现“无提示地重复跳过”。
6. 连续播放多首在线歌曲，确认切歌后旧歌曲的延迟结果不会覆盖当前歌曲。
7. 冷启动和第二次启动分别观察首屏出现时间、搜索/切歌响应和日志中的阶段耗时。

## 风险与回滚

- 收藏和歌单成员关系属于用户数据高风险区域：只调用现有成员 API，不改变 JSON 结构和身份规则。
- 在线源启停涉及注册表和 Node 进程重载：每次操作后都以注册表内容和实际搜索源状态双重核验。
- 在线播放优化可能受网络、音源质量和 Qt 多媒体后端影响：必须区分代码回归与外部网络波动。
- 启动延迟不能把必要的用户数据加载推迟到导致页面错误的程度；若首屏后状态不完整，应回退对应延迟任务。
- 每个实现阶段使用单独、聚焦的本地 commit；若人工验收失败，只回滚本阶段涉及的文件，不恢复或覆盖当前已有 UI V2 改动。

## 设计结论

采用方案 A，先完成阶段一的功能修复，再根据基线数据实施阶段二的局部性能优化。实现前需要再次审查目标文件的当前差异，并保留现有 UI V2 未提交改动。
