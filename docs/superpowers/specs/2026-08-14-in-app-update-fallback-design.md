# 应用内更新与外部安装兜底设计

## 目标

修复 Windows 更新时“更新助手已经启动，但旧安装目录仍被子进程占用，导致 beta3/beta5 更新失败并回滚”的问题，并保留一个可见、可重复使用的外部安装包更新入口。

成功标准：

- 主程序退出后，在线源 Node 运行时、播放器和其他后台进程不再阻塞安装目录替换。
- 更新助手遇到 Windows 文件锁时，在有限时间内重试，而不是第一次失败就回滚。
- 应用内替换仍失败时，旧版本和用户数据保持完整，用户可以使用已校验的完整安装包更新。
- beta3/beta5/beta6 到后续版本的更新链路有自动化回归覆盖。

## 方案选择

### 方案 A：应用内更新优先，外部安装包兜底（采用）

应用内更新继续使用小体积 update ZIP。主程序先关闭运行时，更新助手等待父进程退出并对目录替换做有限重试。更新对话框同时保留“使用安装包更新”路径：它下载并校验完整安装包，交给现有 Inno Setup 流程安装到当前安装目录。

优点是正常更新速度快、失败时有明确的用户可控备用路径，而且不需要让更新助手承担网络下载和安装器逻辑。代价是用户在应用内替换失败后需要重新选择安装包更新；这比静默启动安装程序更安全。

### 方案 B：更新助手失败后自动下载并启动安装器

把完整安装包地址、大小和 SHA-256 传给更新助手，由更新助手在目录替换失败后下载并启动安装器。兜底更自动，但会把网络、校验、安装器启动和失败恢复逻辑集中到一个已脱离主程序的 helper 中，风险和测试成本更高，本轮不采用。

### 方案 C：始终使用完整安装包

稳定性最高，但失去应用内更新的速度和体验，不符合当前产品方向。

## 组件与数据流

### 主程序与更新服务

- 保留现有 manifest 的 `package_*` 和 `setup_*` 两套校验信息。
- 更新对话框在应用内更新包校验成功后，仍显示“立即更新”；同时提供“使用安装包更新”备用动作。
- 备用动作单独下载并校验 `setup_url` 对应的完整安装包，不覆盖已校验的 update ZIP 状态。
- 外部安装包启动成功后，沿用现有关闭主窗口、退出 Qt 事件循环和 Inno Setup `/DIR` 路径固定逻辑。

### 主程序关闭顺序

启动应用内更新后，主窗口先结束更新对话框的嵌套事件循环，再停止在线源客户端、Node runner、播放器和后台服务，最后关闭主窗口并退出 Qt。现有关闭逻辑保持不变，只补充必要的等待/完成信号，避免“父 PID 已退出但子进程仍占用当前工作目录”。

### 更新助手

- 等待父进程退出后解压更新包。
- 对 `os.replace(install_dir, backup_dir)` 增加有限重试，仅针对目录仍被占用的 `PermissionError`/Windows 锁定错误。
- 使用短暂递增间隔，设置总等待上限；成功后才进入新目录替换。
- 超时后不删除旧目录、不覆盖旧目录、不启动损坏的新目录；写入失败日志并启动旧版本。
- 原有 backup/rollback 保护继续保留。

## 外部安装包兜底交互

当用户点击备用动作时：

1. 下载完整安装包到现有更新缓存目录。
2. 校验文件大小、SHA-256 和安装包文件名。
3. 显示“安装程序将接管更新”的确认提示。
4. 启动现有 Inno Setup 安装器，并固定 `/DIR` 为当前安装目录。
5. 安装器启动成功后关闭当前 HushPlayer；失败则保留应用运行，不删除任何目录。

如果应用内更新助手运行阶段失败并回滚，旧版本仍可重新打开设置中的更新对话框，选择同一个外部安装包路径完成恢复。失败日志保留供诊断，但不作为删除或覆盖用户数据的依据。

## 测试设计

### 更新助手回归

- 正常替换：临时安装目录可被新目录替换，旧 backup 清理成功。
- 文件锁重试：模拟 `os.replace` 前几次抛出 Windows 锁定错误，随后成功；验证最终进入新版本。
- 永久锁定：模拟一直失败；验证旧目录仍存在、没有新旧目录互换错误、失败日志可写。
- staging 失败：验证 backup 可以回滚到旧目录。

### 外部安装包回归

- 完整安装包下载请求使用 `setup_url`，不误用 `package_url`。
- 安装包大小和 SHA-256 错误时拒绝启动。
- 启动器失败时不关闭主程序。
- 启动器成功时结束更新对话框并退出主程序。

### 现有链路

- 保留并运行现有 `tests/in_app_update_smoke.py`、`tests/app_update_smoke.py`。
- 运行 Python 编译检查、更新清单校验和 `git diff --check`。
- 发布 beta7 后用 beta3、beta5、beta6 安装目录分别进行人工更新测试；beta6 发布文件不覆盖。

## 风险与回滚

- 这是更新器高风险改动，beta6 提交 `fb42140` 作为回滚点。
- 本轮不修改用户数据结构、音乐库、歌单、播放队列或远端历史。
- 不使用 `git clean`，不删除现有安装目录和正式发布产物。
- 若回归测试发现替换流程异常，可恢复 `packaging/hushplayer_updater.py`、更新服务和对话框相关提交，beta6 仍可继续作为稳定回滚版本。
